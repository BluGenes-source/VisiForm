## Goal 1: Make Corner Radius affect widget rendering

Changing Corner Radius must immediately alter the visible shape of supported widgets.

Trace the complete value path:

1. Property Inspector slider value
2. committed appearance override
3. resolved normal widget style
4. widget rendering helper
5. rounded rectangle or border drawing

Confirm where the value is lost, ignored, overwritten, or rendered incorrectly.

Possible causes include:

- slider updates a temporary UI value but does not commit the model property
- state appearance editing writes to the wrong override scope
- resolved style ignores the widget-level Corner Radius override
- renderer still uses a hard-coded radius
- fill is rounded but border remains square
- border is rounded but selection overlay makes the change difficult to see
- radius units are not DPI- or zoom-adjusted correctly
- the drawing API receives an invalid radius or diameter value

Record the confirmed root cause in the Phase 113 plan.

## Corner Radius behavior

For supported rectangular widgets:

- changing the slider repaints immediately
- both fill and visible border use the resolved radius
- zero, if supported, produces square corners
- larger values produce progressively rounder corners
- radius is clamped safely to the widget dimensions
- radius must not exceed half the smaller widget dimension
- model width and height must not change
- hit testing and widget bounds remain rectangular unless the existing system already supports shape-aware hit testing
- selection outlines and resize handles remain editor geometry and need not become rounded

Do not confuse the Phase 104 resize-corner arcs with the widget’s runtime corner radius.

## Normal versus state appearance

Corner Radius remains a normal geometry/style metric.

Requirements:

- state appearance overrides must inherit the normal Corner Radius
- Hover, Pressed, Focused, Checked/Selected, and Disabled must not replace it
- editing a state must not write Corner Radius into state-specific overrides
- changing the normal Corner Radius must affect all runtime states

## Undo and dirty state

Changing Corner Radius must:

- create the expected undoable property change
- mark the project dirty only when the value changes
- support undo and redo
- repaint immediately after undo and redo
- create no undo entry for a no-op

## Responsive inspector layout

Use practical minimum widths.

Preferred behavior:

- give the property-name column a reasonable minimum width
- allow the editor/value region to use remaining width
- compact or omit redundant range text before clipping the current value
- use elision or a hover hint for long labels when necessary
- keep the numeric current value readable
- recompute layout when the Property Inspector splitter moves

Do not use a single hard-coded width that only matches the current screenshot.

## Slider display

For Corner Radius and Border Thickness:

- show the current numeric value clearly
- show the valid range only if it fits cleanly
- avoid truncated strings such as `25 / 2`
- keep slider movement and typed editing synchronized
- preserve the confirmed property range

If displaying both current and maximum makes the row too crowded, prefer showing only the current value beside the slider and expose the range through the property hint or tooltip.
