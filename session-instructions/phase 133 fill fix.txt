## Goal

Ensure that all widget-owned visual lines for rounded rectangular controls use the same resolved Corner Radius.

For supported rectangular widgets, the following must agree on the same rounded geometry:

- background fill
- border stroke
- highlight edge
- shadow edge
- pressed/recessed edge treatment
- focus outline where applicable

The only lines that may remain square are editor overlays such as:

- selection outline
- resize handles
- resize-corner arcs
- grid/guides

## Root-cause investigation

Trace the drawing path for a representative Button and determine exactly which layer is still rectangular.

Possible causes include:

- fill uses a rounded-rect helper but border uses drawRect
- highlight and shadow edges are still built from straight rectangular line segments
- pressed-state bevel code still assumes square corners
- focus outline uses a separate square-rect path
- one or more layers use hard-coded widget bounds instead of rounded geometry
- the shared style helper returns a radius but not a rounded-rect path
- different layers clamp the radius differently

Record the confirmed root cause in the Phase 113 plan.

## Required rendering fix

For supported rectangular widgets, use one shared rounded-geometry source of truth.

Preferred approach:

- compute the resolved visual rectangle
- compute the effective clamped radius
- build one rounded-rectangle path or equivalent shared geometry description
- use that same rounded geometry for:
  - fill
  - border
  - highlight edge
  - shadow edge
  - focus outline where applicable

Avoid mixing:
- rounded fill
with
- square border/highlight/shadow

If the bevel/highlight system cannot use a single path directly, update it so its visible edge treatment follows the rounded corners rather than drawing a plain rectangle on top.

## Radius behavior

Preserve the current Corner Radius property behavior:

- immediate repaint when changed
- radius clamped safely to half the smaller widget dimension
- zero, if supported, produces square corners
- large values produce strongly rounded corners without self-intersection
- width and height do not change
- hit testing may remain rectangular unless existing infrastructure already supports shape-aware hit testing
