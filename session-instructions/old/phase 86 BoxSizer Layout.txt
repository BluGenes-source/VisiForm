============================================================
WHAT A SIZER IS
===============

A Sizer is a nonvisual layout manager.

It calculates the bounds of its children whenever its own assigned bounds
change.

A Sizer:

* does not represent a visible control at runtime
* does not need a background
* does not need a border
* does not need text
* does not need its own native window
* may have a dashed design-time outline in the VisiForm Designer
* may have a design-time label such as `Vertical Sizer`

The Sizer must manage an ordered sequence of layout items.

A layout item may represent:

* a normal widget
* a nested Sizer
* a fixed spacer
* a stretch spacer

============================================================
SIZER PROPERTIES VERSUS SIZER-ITEM PROPERTIES
=============================================

This distinction is mandatory.

Properties belonging to the Sizer itself include:

* orientation
* padding left
* padding top
* padding right
* padding bottom
* gap
* optional design-time visualization settings

Properties describing how one child participates in its parent Sizer include:

* proportion
* expand
* alignment
* border
* border sides
* minimum width
* minimum height
* shown or participates-in-layout, if compatible with the current model

These child-layout settings belong conceptually to the relationship between
the parent Sizer and the child.

They are not intrinsic visual properties of the child widget.

Inspect the current model before choosing the representation.

Preferred representation:

```cpp
struct ChildPlacement
{
    std::unique_ptr<WidgetNode> child;
    SizerItemLayout layout;
};
```

If changing the existing child relationship structure would be excessively
invasive, a dedicated `SizerItemLayout` value may be stored on the child, but
it must only be interpreted when the child’s direct parent is a Sizer.

Do not duplicate layout metadata in multiple sources of truth.

Do not spread string-based property access throughout unrelated code when
typed helpers, registry metadata, enums, or property abstractions already
exist.

CONCEPTUAL TYPES

The conceptual model should resemble:

```cpp
enum class SizerOrientation
{
    Vertical,
    Horizontal
};

enum class SizerAlignment
{
    Start,

    End

{
    None   = 0,

    Bottom = 1u << 3,

{

    bool expand = false;
    SizerAlignment alignment = SizerAlignment::Start;

    int border = 0;
    SizerBorderSide borderSides = SizerBorderSide::None;

    int minimumHeight = -1;

{

    int paddingLeft = 0;
    int paddingTop = 0;
    int paddingRight = 0;
    int paddingBottom = 0;

    int gap = 0;
};
```

Reuse or extend existing VisiForm types rather than creating duplicate
structures.

Keep these types outside the Visage UI layer when they are part of the model,
serialization, validation, or generation architecture.

============================================================
ORIENTATION AND AXES
====================

A Vertical Sizer arranges items from top to bottom.

A Horizontal Sizer arranges items from left to right.

For a Vertical Sizer:

* main axis is vertical
* cross axis is horizontal

For a Horizontal Sizer:

* main axis is horizontal
* cross axis is vertical

The concepts of proportion, Expand, alignment, minimum size, border, and gap
must use these definitions consistently.

============================================================
PROPORTION
==========

Proportion distributes extra space along the main axis.

A proportion of zero means:

* use the child’s minimum or preferred size along the main axis
* do not receive a weighted share of remaining space

A proportion of zero does not mean zero size.

Positive values are relative weights.

Example:

* Child A: proportion 0, minimum main-axis size 30
* Child B: proportion 1, minimum main-axis size 50
* Child C: proportion 2, minimum main-axis size 50
* remaining extra space: 150

Total positive proportion:

```text
1 + 2 = 3
```

Extra allocation:

```text
Child A: 0
Child B: 150 × 1 / 3 = 50
Child C: 150 × 2 / 3 = 100
```

Final main-axis sizes:

```text
Child A: 30
Child B: 100
Child C: 150
```

Use deterministic remainder distribution.

When integer division leaves pixels unassigned:

* assign them in stable child order, or
* use another documented deterministic method

The same input must always produce the same rectangles.

============================================================
EXPAND
======

Expand controls the cross axis only.

For a Vertical Sizer:

* `Expand = true` fills available width
* `Expand = false` keeps preferred width and uses horizontal alignment

For a Horizontal Sizer:

* `Expand = true` fills available height
* `Expand = false` keeps preferred height and uses vertical alignment

Do not use Expand to allocate main-axis growth.

Main-axis growth is controlled by proportion.

============================================================
ALIGNMENT
=========

Support:

* Start
* Center
* End

For a Vertical Sizer:

* Start means left
* Center means horizontally centered
* End means right

For a Horizontal Sizer:

* Start means top
* Center means vertically centered
* End means bottom

Alignment has no visible effect while Expand is enabled.

That combination may produce an informational validation message, but it must
not be a fatal error.

============================================================
PADDING, GAP, AND BORDER
========================

Keep these concepts separate.

Sizer padding:

* space inside the Sizer around the complete child collection

Gap:

* automatic space between adjacent participating children

Item border:

* space around one child

Border sides:

* determine which sides receive the item border value

Support:

* None
* Left
* Top
* Right
* Bottom
* All

A typed bitmask is preferred if it fits the current codebase.

============================================================
LAYOUT ENGINE
=============

Implement the BoxSizer mathematics as shared, testable layout logic.

The layout engine should:

* depend on model-level geometry types
* not depend on Visage painting
* not depend on Designer selection state
* accept a parent rectangle and ordered layout items
* calculate deterministic child rectangles
* calculate Sizer minimum size
* support nested Sizers recursively
* support fixed and stretch spacers
* safely handle undersized parents

The Designer and generated runtime should use the same algorithm or the same
single source of layout mathematics whenever practical.

Do not maintain two independently written BoxSizer algorithms.

============================================================
PASS 1 — MINIMUM SIZE
=====================

For each participating child:

1. Obtain its intrinsic preferred or minimum size.
2. Apply explicit Sizer-item minimum-width and minimum-height overrides.
3. Add enabled border sides.
4. Record its bordered main-axis minimum.
5. Record its bordered cross-axis minimum.
6. Recursively calculate nested Sizer minimum sizes.
7. Include spacer minimum sizes.

For a Vertical Sizer:

```text
itemMainMinimum =
    childMinimumHeight + topBorder + bottomBorder

itemCrossMinimum =
    childMinimumWidth + leftBorder + rightBorder
```

For a Horizontal Sizer:

```text
itemMainMinimum =
    childMinimumWidth + leftBorder + rightBorder

itemCrossMinimum =
    childMinimumHeight + topBorder + bottomBorder
```

Vertical Sizer minimum:

```text
minimumWidth =
    paddingLeft
    + maximum(itemCrossMinimum)
    + paddingRight

minimumHeight =
    paddingTop
    + sum(itemMainMinimum)
    + totalGap
    + paddingBottom
```

Horizontal Sizer minimum:

```text
minimumWidth =
    paddingLeft
    + sum(itemMainMinimum)
    + totalGap
    + paddingRight

minimumHeight =
    paddingTop
    + maximum(itemCrossMinimum)
    + paddingBottom
```

Total gap:

```text
gap * max(0, participatingChildCount - 1)
```

============================================================
PASS 2 — MAIN-AXIS DISTRIBUTION
===============================

Create the usable content rectangle by subtracting Sizer padding.

Subtract the total gap size from the available main-axis length.

Calculate:

```text
minimumMainTotal =
    sum of bordered item main-axis minimum sizes

extraSpace =
    max(0, availableMainAxisLength - minimumMainTotal)

totalProportion =
    sum of positive proportions
```

Each item begins with its bordered minimum main-axis size.

If:

```text
item.proportion > 0
```

and:

```text
totalProportion > 0
```

then assign its weighted share of `extraSpace`.

Use deterministic integer remainder allocation.

Never produce negative child sizes.

============================================================
CROSS-AXIS PLACEMENT
====================

Remove applicable item borders from the cross-axis slot.

When Expand is true:

* fill all remaining cross-axis space

When Expand is false:

* use the effective preferred cross-axis size
* clamp it to the available space
* apply Start, Center, or End alignment

Ensure all final rectangles remain valid.

* clamp rectangles safely
* avoid integer underflow
* avoid overflow
* avoid crashes
* remain deterministic
* produce an appropriate diagnostic where the validation system supports it

Do not add complex shrink-weight behavior in Phase 86 unless the existing
architecture already supports it cleanly.

============================================================
DOCK, ANCHOR, AND ABSOLUTE BOUNDS
=================================

VisiForm already supports Dock and Anchor.

Use these precedence rules:

* A direct child of a Sizer is positioned and sized by that Sizer.
* Dock does not control the final bounds of a direct Sizer child.
* Anchor does not control the final bounds of a direct Sizer child.
* X and Y do not control the final bounds of a direct Sizer child.
* Width and Height do not directly control the final bounds of a direct Sizer
  child, except where existing preferred/minimum-size behavior deliberately
  uses them.
* A Sizer inside a normal container may itself use existing Dock or Anchor
  behavior.
* A Sizer nested inside another Sizer is controlled by its parent Sizer item
  settings.

In the inspector, disable or annotate inactive properties.

Use wording similar to:

`Position and size are controlled by the parent Sizer.`

Do not delete dormant absolute bounds if they are useful when moving a widget
back to an absolute-layout parent.

Do not allow Dock and Sizer layout to compete for the same child.

VALIDATION RULES
================

Do not run builds or tests through:

* terminal
* PowerShell
* cmd.exe
* CMake commands
* Ninja commands
* repository scripts
* generated scripts

unless the developer explicitly requested the exact command.

Use only the Visual Studio workspace build pipeline when:

* it is available
* it clearly targets `VisiForm`
* it is unambiguous

Never validate against `freetype.vcxproj`.

Do not launch the application after building.

Do not launch generated applications.

When the approved workspace build is unavailable or ambiguous:

* do not substitute another build method
* record build validation as deferred to the developer
* provide the developer with the exact target that should be built manually
* do not falsely claim that the code compiled

============================================================
WORKING RULES
=============

* Work incrementally.
* Preserve current functionality.
* Avoid unrelated refactoring.
* Follow existing naming and formatting.
* Follow existing ownership conventions.
* Avoid raw owning pointers.
* Avoid duplicate sources of truth.
* Keep layout calculation separate from painting.
* Keep model and generator code free of Visage UI headers.
* Put Visage-specific UI work in the UI layer.
* Use `WidgetRegistry`.
* Update `WidgetDefinition` where required.
* Preserve CRLF.
* Preserve static runtime settings.
* Preserve CMake presets.
* Preserve the vcpkg triplet.
* Preserve generated `MainWindow`.
* Preserve USER CODE regions.
* Preserve safe export ownership rules.
* Do not claim cross-platform validation unless it was actually completed.
* Do not claim successful compilation unless approved validation succeeded.
