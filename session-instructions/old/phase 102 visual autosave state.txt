## Required state semantics

Preserve these distinct states:

### Dirty project

The title-bar asterisk means the main project file contains unsaved changes.

Recovery autosave must not:

* remove the asterisk
* mark the model clean
* reset normal Save enablement
* change the main project file timestamp
* make closing the project skip the unsaved-changes prompt

### Recovery autosaved

A successful recovery autosave means a separate recovery copy exists.

It must not be treated as a normal project save.

### Manually saved

Only a successful Save or Save As may:

* clear the dirty state
* remove the title-bar asterisk
* clean up the associated recovery file
* reset the recovery timer

## Goal 1: Add visible autosave status

Use the existing VisiForm status area.

Display concise status messages:

* `Autosaving recovery…`
* `Recovery autosaved at <time>`
* `Recovery autosave failed: <brief reason>`
* `Project saved` after a successful normal Save or Save As

Requirements:

* show the success message only after the recovery file has been written successfully
* include the local time of the completed autosave
* do not use a modal dialog for normal autosave success
* do not repeatedly overwrite a more important active error message
* autosave failure should remain visible long enough to be noticed
* repeated failures should not open repeated dialogs

Prefer the wording `Recovery autosaved` rather than only `Autosaved`, so users do not mistake it for a normal project save.

## Goal 2: Make autosave state inspectable

Track editor-only autosave status such as:

* idle
* waiting
* writing
* succeeded
* failed

Also track:

* last successful recovery autosave time
* last error message, if any
* recovery-file path internally for diagnostics

Do not store these values in `.vfb.json`.

The UI does not need to display the recovery path during normal use.

## Goal 3: Add a practical testing path

The normal autosave interval may remain five minutes, but provide a safe way to validate it without waiting repeatedly.

Preferred options, in order:

1. Existing debug configuration uses a short interval, such as 15 or 30 seconds.
2. Add a debug-only `Autosave Recovery Now` command.
3. Make the interval a clearly named development constant that can be temporarily changed.

Do not expose a permanent end-user command unless it fits the existing UI cleanly.

Do not leave the release interval at an excessively short test value.

Record the testing method in the Phase 102 plan.

## Goal 4: Verify the timer actually runs

Trace and confirm:

* the autosave timer starts after a project becomes active
* dirty-state changes are visible to the timer callback
* the callback runs after the configured interval
* autosave is skipped for an unmodified project
* autosave is skipped during save/load or unsafe modal state
* a successful write updates the status message and timestamp
* a failed write reports failure
* callbacks stop safely during shutdown

If autosave is not firing, fix the actual timer ownership or callback issue rather than only adding UI messages.
