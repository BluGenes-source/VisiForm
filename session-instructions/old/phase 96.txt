## Goal 1: Remove Recent Files from the Project Tree

Remove the Recent Files list currently displayed below the widget entries.

Requirements:

* remove the Recent Files heading and entries from the Project Tree panel;
* remove any related layout code that reserves space inside the Project Tree;
* preserve recent-file functionality elsewhere if it already exists in menus or another appropriate location;
* do not remove recent-file persistence unless it is used only by this panel and is confirmed obsolete.

The Project Tree panel should be dedicated to the active project hierarchy.

## Goal 2: Replace the Flat List with a Real Tree View

Replace the current shallow Project Tree display with a hierarchical tree that mirrors the actual widget ownership and layout structure.

Use the wxWidgets-style Object Tree screenshot only as a behavioral reference.

The tree should represent:

* project or document root;
* top-level form or window;
* child widgets;
* nested containers;
* sizers and layout objects;
* widgets contained inside sizers;
* panels, tab pages, group boxes, frames, and other supported parents;
* deeper nested descendants.

Use the existing project model as the source of truth.

Do not maintain a separate duplicate hierarchy.

## Tree Behavior

Required behavior:

* parent-child indentation;
* expand and collapse controls;
* clear selected-row state;
* selection of a tree item selects the same widget on the canvas;
* selection on the canvas selects and reveals the same tree item;
* adding a widget inserts it in the correct hierarchy position;
* deleting a widget removes it and its descendants;
* reparenting or moving a widget updates the tree;
* loading a project rebuilds the tree correctly;
* new projects start with the correct root structure;
* renaming a widget updates its tree label;
* widget type remains visible where practical.

Suggested label format:

`widgetName : WidgetType`

Use existing names and type metadata. Do not alter stored widget names.

## Hierarchy Rules

Derive hierarchy from the actual model relationships.

Examples:

* a widget inside a Panel appears beneath that Panel;
* a widget inside a Sizer appears beneath that Sizer;
* nested Sizers appear beneath their owning Sizer or container;
* tab pages appear beneath their Tab Control;
* widgets on a tab page appear beneath that page;
* the top-level form appears beneath the project root.

Do not flatten sizers or containers merely for display convenience.

If layout objects and visual widgets use different model types, introduce the smallest shared tree-node adapter needed.

## Tree State

Preserve reasonable UI state during refreshes:

* expanded branches should remain expanded when possible;
* the selected item should remain visible;
* routine property changes should not collapse the entire tree;
* avoid rebuilding the entire tree for every small change when a focused update is practical.

A full rebuild is acceptable for project load, new project, or major hierarchy changes.

## Visual Design

Use the existing VisiForm visual style.

Include:

* indentation guides or equivalent hierarchy spacing;
* expand/collapse indicators;
* widget icons if existing icons are readily reusable;
* readable labels;
* clipping or elision for long names;
* vertical scrolling;
* horizontal scrolling only if needed.

Do not copy wxWidgets styling exactly.
Do not introduce a second UI framework.

## Selection and Commands

Preserve existing behavior for:

* canvas selection;
* Property Inspector synchronization;
* Events tab synchronization;
* Delete;
* undo and redo;
* copy and paste;
* multi-selection behavior, if currently supported.

For multi-selection, keep the current primary-selection behavior unless the existing model already supports multiple selected tree rows.

## Architecture

Prefer reusing:

* the current project model;
* existing parent-child relationships;
* selection controller;
* widget registry metadata;
* existing command notifications;
* existing tree or list controls in Visage.

Do not change:

* `.vfb.json` format;
* generator behavior;
* validation rules;
* widget ownership semantics;

unless a small correction is required to expose an already-existing hierarchy.
