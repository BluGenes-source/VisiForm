## Goal 1: Add Fit Width to Parent

Add a visible Layout menu command:

`Fit Width to Parent`

This command applies to compatible selected widgets.

Required behavior:

* set the widget width to the usable width of its direct parent
* constrain the widget within the parent’s left and right content edges
* change width only
* preserve the widget’s existing height
* preserve vertical position
* set or clamp horizontal position as needed to fit within the parent
* use model-space geometry
* create one undoable command
* create no undo entry for a no-op

The resulting geometry should conceptually be:

* `x = parent content-left inset`
* `width = parent usable content width`

Do not use application-window or canvas viewport width.

## Goal 2: Add Fit Height to Parent

Add a visible Layout menu command:

`Fit Height to Parent`

Required behavior:

* set the widget height to the usable height of its direct parent
* constrain the widget within the parent’s top and bottom content edges
* change height only
* preserve the widget’s existing width
* preserve horizontal position
* set or clamp vertical position as needed to fit within the parent
* use model-space geometry
* create one undoable command
* create no undo entry for a no-op

The resulting geometry should conceptually be:

* `y = parent content-top inset`
* `height = parent usable content height`

Do not use application-window or canvas viewport height.

## Parent-content bounds

Use the direct parent’s usable child-content area, not merely its outer visual rectangle.

Account for existing parent characteristics where available:

* borders
* title/header areas
* content padding
* frame or group-box captions
* tab-page content area
* container insets
* scrollable content bounds
* layout-controlled regions

Use existing model or widget metadata for content bounds when possible.

Avoid hard-coding special offsets in the menu command.

Prefer one shared helper that returns parent-local child-content bounds.

## Supported parents

Verify behavior for widgets directly inside:

* top-level form
* Panel
* Frame
* Group Box
* tab page
* other existing free-position containers

The command must use the selected widget’s direct parent.

Do not fit a widget to a grandparent merely because the direct parent has a similar visual size.

## Sizer-managed widgets

For widgets whose geometry is controlled by a Sizer:

* do not directly overwrite sizer-owned geometry
* disable Fit Width or Fit Height when the operation is incompatible
* use existing layout metadata only if there is already a safe mapping
* do not detach or reparent the widget
* do not silently break the sizer layout

Document the chosen rule in the phase plan.

## Selection behavior

For the base implementation:

* allow the command for one or more compatible selected widgets
* each selected widget fits to its own direct parent
* mixed-parent selections are acceptable only if each item can be processed independently and predictably
* skip or disable incompatible selections rather than partially corrupting layout
* preserve selection after execution

If the existing command system cannot safely support mixed parents, require compatible same-parent selection and document that restriction.

## Command enablement

Update the Layout menu state dynamically.

Enable Fit Width to Parent or Fit Height to Parent only when:

* at least one widget is selected
* the selected item has a valid parent content area
* the affected dimension is not controlled incompatibly by a sizer
* Preview Mode is not active
* the operation is valid for the widget type

Do not enable a command that will do nothing or produce invalid geometry.

Keep existing `Fit Text` behavior separate.

## Undo and redo

Each successful command invocation must produce one undo step.

Requirements:

* undo restores original position and dimensions
* redo reapplies the complete operation
* multiple selected widgets are included in the same command
* no-op or rejected operations create no undo entry
* Project Tree and Property Inspector remain synchronized

Reuse the existing command system.

## Correct placement behavior

Every newly created widget must be fully inside its intended parent where possible.

For default startup and New Project widgets:

* establish the parent/form dimensions first
* use a modest inset inside the direct parent’s content area
* store parent-local model coordinates
* ensure the full widget rectangle is within parent content bounds
* produce the same valid result at startup and through New Project

For palette click-to-create:

* choose a valid default position inside the active target parent
* use parent-local model coordinates
* clamp the full widget rectangle inside parent content bounds

For drag/drop:

* convert pointer coordinates from view space to model space
* then convert to the selected parent’s local coordinate system
* clamp only when necessary
* preserve the intended drop location as closely as possible

Do not fix the problem only in drawing.
Do not offset the visual rectangle while leaving invalid stored coordinates.

## Shared geometry helpers

Prefer small shared helpers for:

Reuse these helpers for both:

* Fit Width/Fit Height commands
* new-widget safe placement

Do not duplicate slightly different parent-bound calculations across creation paths.
