## Goal

Refine the shared runtime styling so widget interaction states are visually consistent and Preview Mode more closely matches generated runtime output.

Focus on:

- normal
- hover
- pressed
- focused
- checked
- selected
- disabled
- active/inactive
- read-only where already supported

Do not add new widget behavior merely to demonstrate styling.

## Shared state policy

Create or refine one shared state-resolution path.

Prefer a compact state description that represents:

- enabled
- hovered
- pressed
- focused
- checked or selected
- active
- read-only where relevant

Avoid independent priority rules in every widget.

Define a predictable visual priority.

Suggested priority:

1. disabled
2. pressed
3. checked or selected
4. hovered
5. focused overlay
6. normal

Focus may be rendered as an additional outline rather than replacing the base state.

Document the final priority order.

## State consistency

Use shared style primitives for equivalent states.

Examples:

- disabled controls should use consistent reduced contrast
- hover should use consistent modest emphasis
- pressed controls should appear recessed
- selected or checked controls should remain clearly distinguishable
- focus indication should be visible but not obscure text or borders
- active tabs should connect visually to their page
- inactive tabs should remain readable
- splitter hover should match its actual drag area

Do not make all controls visually identical. Preserve widget-specific structure.

- normal raised state

- pressed recessed state
- focus indication
- disabled appearance
- text remains centered in every state

Ensure pressed geometry does not change saved bounds.

## Preview Mode

Preview Mode should use runtime-like state rendering.

Requirements:

- no editor-only labels
- no selection handles
- no resize arcs
- no guides
- temporary interactions may display hover, pressed, checked, or selected state
- temporary state must not modify the project model
- leaving Preview Mode discards preview-only state

Do not add generated event-handler execution.

## Generated output parity

Compare the styled widgets in:

- Design Mode
- Preview Mode
- generated runtime application

Prioritize fixing confirmed differences in:

- colors
- border widths
- highlight/shadow direction
- corner radius
- state transitions
- padding
- text alignment
- disabled-state contrast
- focus indication

Reuse shared constants or generated equivalents where practical.

Do not duplicate large style tables in generated code if a smaller shared helper is appropriate.

Preserve generated-code readability and `USER CODE` regions.

## Parity policy

Exact pixel parity is not required where the designer and generated application use different rendering infrastructure.

Required goal:

- same visual intent
- same state hierarchy
- similar spacing and dimensions
- consistent raised/recessed direction
- no obvious fallback to old styling

Record remaining differences rather than hiding them.

## DPI and zoom

Verify:

- borders remain crisp
- focus outlines remain visible
- shadow/highlight edges do not blur excessively
- state styling remains readable at supported zoom levels
- generated runtime behaves correctly at normal DPI and available scaled DPI testing

Avoid fixed pixel values where existing DPI helpers should be used.

## Internal names

Preserve the Phase 105 rule:

- internal names are editor metadata
- no internal names in Preview Mode
- no internal names as runtime captions
- only explicit runtime text properties are rendered
