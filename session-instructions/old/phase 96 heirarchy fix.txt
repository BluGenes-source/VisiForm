Bug: when a Frame is added and then another widget is added inside that Frame, the Project Tree does not show the widget as a child of the Frame. The canvas ownership appears correct, but the tree displays the new widget at the wrong hierarchy level.

Keep this pass narrow and token-efficient.

Rules:

- no subagents
- read only the active Phase 96 plan and files directly related to:
  - widget parent/child ownership
  - Frame containment
  - Project Tree node construction and refresh
  - add/reparent notifications
  - undo/redo hierarchy updates
- do not perform a repository-wide audit
- do not refactor unrelated tree formatting or tooltip code
- build once after the focused fix

Tasks
=====

1. Confirm the source-of-truth relationship
-------------------------------------------

Trace the exact path when a widget is added inside a Frame:

- how the canvas determines the drop target
- where the child widget's parent/container is assigned
- whether the Frame owns the child in the model
- which notification or refresh reaches the Project Tree
- whether the tree uses model ownership, canvas geometry, or stale cached parent data

Record the confirmed root cause in the Phase 96 plan.

2. Fix Frame child hierarchy
----------------------------

Ensure widgets added inside a Frame appear beneath that Frame in the Project Tree.

Requirements:

- use the actual model parent-child relationship
- do not infer hierarchy only from visual overlap
- avoid Frame-specific duplicate hierarchy logic if a shared container path exists
- preserve correct ordering among Frame children
- update immediately after add or reparent
- do not require project reload to show the correct parent

3. Verify all supported container paths
---------------------------------------

Use the same hierarchy update path for other existing containers where applicable, including:

- Panel
- Group Box
- Frame
- Sizer
- tab page/container nodes

Do not broaden into a redesign. Only correct shared logic directly implicated by the Frame bug.

4. Preserve tree state
----------------------

When correcting or refreshing the affected branch:

- keep the Frame expanded when practical
- preserve selection
- reveal the newly added child
- avoid collapsing unrelated branches
- clear or update hover hints safely
- avoid rebuilding the entire tree when a focused branch update is sufficient

A full rebuild is acceptable only if that is the existing correct mechanism and it preserves state.

5. Undo, redo, move, and load
-----------------------------

Verify hierarchy remains correct when:

- adding a widget to a Frame
- undoing the add
- redoing the add
- moving or reparenting a widget into a Frame
- moving it back out
- deleting the Frame
- saving and reloading the project

Do not change `.vfb.json` unless the model relationship is genuinely not being persisted.
