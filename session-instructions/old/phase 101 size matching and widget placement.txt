## Goal 1: Expand Same Width and Same Height

Refine the existing sizing commands so selected widgets can match:

* the primary selected widget
* the smallest selected widget
* the largest selected widget

Use visible menu commands rather than requiring an undocumented modifier key.

Preferred menu structure:

* Same Width

  * Match Primary
  * Match Smallest
  * Match Largest
* Same Height

  * Match Primary
  * Match Smallest
  * Match Largest

If the current menu system cannot support submenus cleanly, use clearly named separate commands.

Do not remove the existing primary-widget behavior.

## Size reference rules

### Match Primary

Use the existing primary selected widget as the reference.

### Match Smallest

* Same Width: use the smallest width among compatible selected widgets.
* Same Height: use the smallest height among compatible selected widgets.

### Match Largest

* Same Width: use the largest width among compatible selected widgets.
* Same Height: use the largest height among compatible selected widgets.

Requirements:

* reference calculation uses model-space dimensions
* all compatible selected widgets receive the reference dimension
* preserve positions unless resizing constraints require otherwise
* do not change the unaffected dimension
* respect minimum sizes
* respect fixed-size widgets
* protect sizer-managed dimensions
* require at least two compatible sibling widgets
* disable commands for incompatible cross-parent selections
* no-op operations must not create undo entries

## Optional modifier behavior

Do not make modifier keys the only way to access these commands.

A modifier shortcut may be added only if it fits the existing command system cleanly and remains documented.

Do not add hidden Ctrl-click behavior directly to menu items without visible command equivalents.

## Undo and redo

Each sizing action must create one undoable command.

Requirements:

* one action creates one undo step
* undo restores all original dimensions
* redo reapplies the selected sizing mode
* selection remains stable
* no-op commands do not dirty the project

Reuse the existing Phase 100 command path.

## Goal 2: Fix initial default-widget placement

When VisiForm starts or creates a new project, the default Button can appear partially outside the form or canvas.

Trace the initial placement path and determine whether it uses:

* stale canvas dimensions
* viewport coordinates instead of model coordinates
* form bounds before layout completes
* zoom or pan offsets incorrectly
* hard-coded placement values
* incorrect centering calculations

Fix the root cause.

Requirements:

* the default widget must be fully inside the top-level form
* placement must use form/model bounds, not application-window coordinates
* placement must work at any zoom or pan state
* placement must remain correct after window resizing
* opening VisiForm must show a valid initial project
* creating a new project must produce the same valid placement

Do not merely clamp the rendered rectangle while leaving incorrect model coordinates.

## Goal 3: Fix placement of newly created widgets

Widgets created from the top palette can also appear partially outside the form.

Ensure newly created widgets are placed fully inside their intended parent.

For click-to-create behavior:

* choose a safe default position inside the active form or container
* include a modest inset from the parent edges
* account for the new widget’s default size
* clamp the complete widget bounds inside the parent
* convert view coordinates to model coordinates when zoom or pan is active

For drag/drop creation:

* use the drop point in model space
* clamp only when necessary to keep the widget inside the valid parent
* preserve correct container targeting
* do not incorrectly reparent due to visual overlap

If the widget is larger than the available parent area, place it at the parent inset and preserve its valid minimum/default size rather than producing invalid negative coordinates.

## Shared placement helper

Prefer one small shared helper for safe initial placement.

It should accept:

* parent model bounds
* desired widget size
* preferred model-space position
* edge inset

It should return a position that keeps the complete widget inside the parent where possible.

Use it for:

* initial default widgets
* new-project widgets
* palette click-to-create
* other directly related creation paths

Do not replace explicit user drag positioning unnecessarily.

## Coordinate integrity

All placement calculations must use model-space coordinates.

Account for:

* canvas zoom
* canvas pan
* form origin
* nested container origin
* border or content inset where relevant

Do not save viewport coordinates into widget geometry.
