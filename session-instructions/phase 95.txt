## Goal

Replace the current vertical Widget Palette on the left side of the application with a horizontal tabbed widget palette near the top of the main window.

Use the provided wxWidgets-style screenshot only as a layout reference. Do not copy its visual styling exactly.

The new palette should appear below the menu/main toolbar and above the primary workspace.

## Required layout

Create a tabbed palette with logical widget categories.

Suggested categories:

* Common
* Containers
* Layout
* Forms
* Data
* Menu/Toolbar
* Additional

Use only categories that make sense for the widget types currently supported by VisiForm.

Assign widgets based on the existing widget registry or widget metadata. Avoid maintaining a second unrelated list of widget definitions.

The selected tab should display a horizontal row or compact wrapped area of widget buttons.

Each widget entry should show:

* its existing icon when available;
* a readable label or tooltip;
* clear selected, hover, and pressed states where supported.

## Behavior

Preserve the current Widget Palette behavior:

* creating widgets;
* drag-and-drop, if currently supported;
* click-to-create, if currently supported;
* widget type lookup;
* selection synchronization;
* canvas placement;
* undo/redo integration;
* Project Tree updates.

Do not create a second widget-creation path.

Reuse the current palette actions and registry wherever possible.

## Main-window cleanup

After moving the palette:

* remove the old left-side Widget Palette panel;
* allow the Project Tree to occupy the appropriate left-side region;
* give the Designer Canvas more horizontal space;
* preserve the Property Inspector layout and splitter behavior from earlier phases;
* avoid leaving empty space or unused splitter children.

The top palette must not cause the main workspace to become excessively short.

Use a compact fixed or preferred height and allow horizontal wrapping or scrolling if needed.

## Responsive behavior

Verify the palette at normal and maximized window sizes.

Requirements:

* tabs remain readable;
* widget controls do not overlap;
* narrow windows remain usable;
* long categories may scroll or wrap cleanly;
* the palette does not grow vertically without a reasonable limit;
* maximizing and restoring the app does not distort the main workspace.

## Architecture

Prefer:

* the existing widget registry;
* reusable Visage tab controls;
* existing toolbar/button controls;
* existing palette event handlers;
* existing layout widgets.

Do not introduce:

* duplicate widget metadata;
* a separate UI framework;
* hard-coded widget creation logic;
* unrelated redesigns.

If category metadata does not exist, add the smallest practical category field or mapping near the registry.

Keep model, serialization, and generator behavior unchanged unless the palette implementation genuinely requires a small compatibility update.
