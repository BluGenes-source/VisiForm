## Goal

Limit the Project Tree width according to the longest currently visible rendered tree row, plus a modest readability buffer.

Do not use a fixed width from the screenshot.

Do not use 125 pixels as a constant. That value was only an example of adding extra space beyond measured content.

## Content-width calculation

Measure the full width required by each visible tree row using the actual Project Tree font metrics.

The measurement must include:

* hierarchy indentation for the row depth
* expand/collapse control and spacing
* optional icon and spacing
* complete rendered label
* normal left and right padding
* vertical-scrollbar allowance when present
* a modest readability buffer after the content

Conceptually:

`required width = indentation + controls + icon + label + padding + buffer`

Use the widest currently visible row as the content-derived width.

Do not use character counts or fixed-width font estimates.

## Width policy

Define three values:

### Minimum width

A practical width that keeps:

* the Project Tree title readable
* expand/collapse controls usable
* short rows recognizable

### Preferred width

The width required by the longest visible row plus the normal readability buffer.

Use this for the initial/default splitter position when there is no valid saved or user-selected position.

### Maximum width

Cap the Project Tree close to its content-derived preferred width.

The maximum may include a small additional drag margin beyond the preferred width, but must not allow large unused empty space.

The intent is:

* the Project Tree can be made narrower by the user
* it can be widened enough to display its visible content comfortably
* it cannot be dragged substantially wider than its content requires
* the Designer Canvas retains the reclaimed workspace

Do not use a large percentage-based maximum that allows the tree to dominate the window.

Still enforce the Designer Canvas minimum width in case the application window is narrow.

## Example behavior

If the complete longest visible row requires a measured width of 260 pixels and the selected readability buffer is 20 pixels, the preferred width would be approximately 280 pixels.

The actual values must come from current font and row measurements rather than this example.

## Manual resizing

Preserve splitter dragging.

Required behavior:

* dragging left reduces the tree to its minimum width
* dragging right stops at the calculated maximum width
* do not snap continuously while the user is dragging
* preserve the user-selected width while it remains within the valid range
* clamp the width only when it falls outside recalculated limits
* do not automatically expand the panel merely because a longer row becomes visible
* allow existing text elision and hover hints to handle content beyond the allowed maximum

## Visible-row policy

Base the measurement on rows currently visible through expanded branches.

Collapsed descendants must not affect the preferred width.

Recalculate limits when relevant events occur, including:

* branch expansion or collapse
* node addition or removal
* rename
* reparenting
* project load
* font or DPI change
* workspace resize

Avoid recalculating on every paint when the hierarchy and font metrics have not changed.

## Deep and unusually long rows

For deeply nested or unusually long labels:

* enforce a practical application-level maximum if necessary to protect the Designer Canvas
* elide text that cannot fit
* preserve the complete row text for the existing hover hint
* do not allow one extreme row to consume most of the application width

The practical maximum should be derived from available workspace and the Designer Canvas minimum width, not from an arbitrary fixed screenshot coordinate.
