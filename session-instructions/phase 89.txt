Work on VisiForm Phase 89: Add Property Inspector Tabs and Move Widget Events to an Events Tab.

Use the configured VisiForm subagents and follow all repository instructions, including the shared agent rules, `copilot-instructions.md`, `visiform.instructions.md`, phase documentation requirements, and the existing VisiForm architecture.

Phase 89 is already assigned. Do not select or substitute another phase number for this task.

## Objective

Update the Property Inspector so that it uses tabs and separates widget properties from widget events.

The inspector currently displays event properties in an `Events` section near the bottom of the same scrolling property list as normal properties. This makes event editing difficult to find and requires unnecessary scrolling.

Change the Property Inspector to contain two tabs:

1. `Properties`
2. `Events`

The normal widget properties must remain on the `Properties` tab.

The widget’s supported events must appear on the `Events` tab.

Use the supplied screenshot as a visual reference for the current layout and the event rows that need to be moved.

## Required behavior

### Properties tab

The `Properties` tab must contain the current property inspector content, including categories such as:

* Hint
* Dock
* Anchor
* Tab Index
* Style
* Look and Feel
* Fill Color
* Text Color
* Border Color
* Accent Color
* Border Thickness
* Corner Radius
* Font Size
* Font Family
* Bold
* Italic
* other widget-specific properties

Do not display the current `Events` category or event rows on the `Properties` tab after this change.

### Events tab

The `Events` tab must display the events supported by the currently selected widget.

Examples currently visible in the inspector include:

* On Click
* On Release
* On Double Click

The exact event list must come from the selected widget’s existing event metadata, property model, or supported-event definitions. Do not hard-code only these three events if the architecture already supports additional widget-specific events.

Each event row must preserve its existing editing behavior, including:

* displaying the current event-handler name or value
* allowing the value to be edited
* committing changes to the selected widget
* participating in undo/redo where currently supported
* updating when the selection changes
* clearing or disabling correctly when no widget is selected
* preserving serialization and project reload behavior

## Tab layout requirements

Add a tab control within the Property Inspector beneath the `Property Inspector` title area.

Preferred tab labels:

* `Properties`
* `Events`

The selected tab must visually match the existing VisiForm theme.

The tabs must:

* fit within the current Property Inspector width
* remain visible while the tab content scrolls
* have independent content panels
* use the available inspector area below the tab strip
* preserve the existing vertical scrollbar behavior
* not create nested or duplicate scrollbars unless required by the current UI architecture
* resize correctly when the Property Inspector panel changes size

The `Properties` tab should be selected by default unless the project already has a consistent mechanism for remembering the previously selected inspector tab.

Do not allow the tab strip itself to scroll out of view with the property rows.

## Selection behavior

When the selected widget changes:

* refresh the Properties tab with the selected widget’s properties
* refresh the Events tab with the selected widget’s supported events
* preserve the currently selected tab where practical
* avoid stale values from the previously selected widget
* avoid rebuilding unrelated UI more often than necessary

When no widget is selected:

* show an empty or disabled Properties tab
* show an empty or disabled Events tab
* do not retain editable event values from the previous widget

When multiple selection is supported:

* preserve current multi-selection behavior for normal properties
* only show event values that can be safely represented for the selection
* if event editing for multiple selection is unsupported, disable or clearly omit the event editor rather than applying an unsafe partial update

## Architecture requirements

Reuse the existing property-inspector row-generation and editor infrastructure.

Do not create a second unrelated event editor implementation if the existing event rows already use the generic property-row system.

Prefer one of these approaches, depending on the current architecture:

* filter the existing inspector property model into Properties and Events collections
* route event-category rows to the Events tab
* create two inspector content containers that share the existing row factory
* use the existing property category/type metadata to determine which tab owns each row

Avoid identifying events only by visible label text.

Use an explicit category, metadata flag, property type, event descriptor, or existing event-definition model where available.

Preserve:

* property binding
* change notification
* selection synchronization
* editor creation
* undo/redo integration
* serialization
* theme styling
* keyboard navigation
* focus behavior

Do not duplicate property ownership between the two tabs.
